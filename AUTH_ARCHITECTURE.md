# Auth Module Architecture Reference

Detailed companion to `SKILL.md`. This documents what actually exists in this repo (Angular ~20.3, standalone components, zoneless change detection, `@ngrx/signals` + hand-rolled RxJS stores, PrimeNG UI) as of the auth-module refactor in commit `f681bd8` ("refactor auth module", author `ferdousr3`). Every claim below is grounded in a real file; paths are relative to `src/`. Where something is unclear, unused, or inconsistent, it's called out explicitly rather than smoothed over — check the "Known gaps" list in `SKILL.md` before treating any single flow as a template to copy verbatim.

## 1. Store utility layer (`libs/store`)

Barrel: `libs/store/index.ts` re-exports everything in `libs/store/lib/`.

- **`state-subject.ts` — `StateSubject<T>`**: extends RxJS `BehaviorSubject<T>`. `value$` is the subject's stream piped through `distinctUntilChanged` using `radash`'s deep-equal `isEqual` (so consumers don't re-fire on referentially-new-but-deep-equal state). `update(value)` is just `next`. `reset()` replaces current value with the constructor's original value (kept in `initialValue`).
- **`simple-store.ts` — `SimpleStore<T>`**: the workhorse. Wraps a `StateSubject<T>` plus its own `unsubscriber: Subject<void>` (defaults to a fresh one, or accepts an external one so multiple stores can share a teardown signal).
  - `setState(value: Partial<T>, sideEffectFn?)`: shallow-merges into current state, then runs an optional side effect.
  - `getState(): T`, `select<K>(key, filterFn?)`: maps to `state[key]`, applies an optional filter, `distinctUntilChanged` (deep-equal), `share()`, and `takeUntil(this.unsubscriber)`. `selectAll()` is the same without the key projection.
  - `reset(sideEffectFn?)` / `destroy()` (completes the unsubscriber, terminating all `select`/`selectAll` streams).
  - This is the base class for feature state services that need loading/error/success-style shape, e.g. `OtpStateService`, `ForgotPasswordStateService` (both `extends SimpleStore<...State>`).
- **`query-result-store.ts` — `QueryResultStore<Q,R,T> extends SimpleStore<{query,result,transient}>`**: adds `query$/result$/transient$` selectors, `setQuery/getQuery`, `setResult/getResult` (also writes into an in-memory `Map` cache), `setTransient/getTransient`. `getCacheKey()` serializes the current query via `qs.stringify(shake(query), {encode:false, sort:...})` (`shake` from `radash` strips falsy keys) so different query-param combinations get distinct cache entries. `getCachedResult()`/`cacheResult()` read/write that map directly. Intended for list/search screens that want to cache a result set per filter combination; **not currently used anywhere in the auth module itself** — it's a generic building block, not something login/signup/OTP touch.
- **`local-storage-store.ts` — `LocalStorageStore<T>`**: same `setState/getState/select/destroy` shape as the in-memory stores, but backed directly by `WA_LOCAL_STORAGE` (from `@ng-web-apis/common`) instead of a subject — every `setState` immediately serializes the whole object to one localStorage key. Constructor takes a `key` and optional `initialState`, seeding localStorage if the key is empty. No reactive stream (no `select` returning an `Observable` — it returns the value synchronously), so it's for persisted-but-not-watched state.
- **`storage-signal.ts` — `storageSignal<T>(key, defaultValue, options?)`**: an Angular `signal()` initialized from `localStorage` (or any `Storage`), that persists on every change via an `effect()`, with cross-tab sync via the `window` `storage` event (only applied if `ev.key` matches and the event didn't originate from the same tab). Uses `destr` for safe deserialization by default. Independent of the class-based stores above — this is the signal-idiomatic equivalent.
- **`@ngrx/signals` feature helpers** — for `signalStore(...)`-style state (used by `RootAppStore` in `app.store.ts`, not by the RxJS-based feature stores):
  - `with-loading.ts` — `withLoading()`: adds `{ isLoading: false }` state + `setLoading(value)`.
  - `with-local-storage-sync.ts` — `withLocalStorageSync(storageKey)`: adds `saveToLocalStorage()` (walks every signal in state, serializes to one JSON blob under `storageKey`) and `loadFromLocalStorage()` (`patchState` from that blob) — both are **manual**, you must call them yourself; nothing calls them automatically.
  - `with-logger.ts` — `withLogger(name)`: registers an `onInit` hook that runs `effect(() => { const state = getState(store) })` — it reads state on every change but **does not actually log anything** (`_name` param is unused, no `console.log` call). This is a stub/incomplete despite the name — don't assume it produces log output.
  - `with-saver.ts` — `withSaver(name, exclude=[])`: on init, runs an `effect()` that on every state change calls `LocalStorageService.setItem(name, JSON.stringify(omit(state, exclude)))` — this one *does* auto-persist, unlike `withLocalStorageSync`.
  - `app.store.ts` — `RootAppStore`: `signalStore({providedIn:'root'}, withState<AppState>({appName, loading}), withMethods(startLoading/stopLoading/setLoading/setAppName))`. A minimal example of composing these; the auth module does not use `RootAppStore` itself.

**Practical implication:** there are two parallel state paradigms in this codebase — RxJS class stores (`SimpleStore` family) for most feature state, and `@ngrx/signals` `signalStore` + feature-helpers for global/app-level state. The auth-adjacent feature libs use the RxJS family exclusively (`OtpStateService`, `ForgotPasswordStateService` extend `SimpleStore`; the CRUD `*-state.service.ts` files use a bare `BehaviorSubject` directly, see §3). Don't mix paradigms within one feature without a reason.

## 2. Auth core (`libs/auth`)

Barrel `libs/auth/index.ts` exports: injector tokens, both interceptors, login model/form-service, `JwtService`, `TokenStorageService`, signup model/form-service. (Notably it does **not** export `AuthService`, `ContextUserStorageService`, `role.consts`, or either API service — those are imported by their full paths where needed, e.g. `libs/auth/login/login-api.service`.)

- **`injector/auth-injector.ts`**: five `InjectionToken`s — `AUTH_API_URL`, `CONTEXT_USER_ID`, `CONTEXT_USER_ROLE`, `ACCESS_TOKEN_KEY`, `REFRESH_TOKEN_KEY`. Provided with concrete values in `app/app.config.ts:42-47`:
  ```ts
  { provide: AUTH_API_URL, useValue: environment.authApiUrl },
  { provide: CONTEXT_USER_ID, useValue: 'contextUserId' },
  { provide: CONTEXT_USER_ROLE, useValue: 'contextUserRole' },
  { provide: ACCESS_TOKEN_KEY, useValue: 'accessToken' },
  { provide: REFRESH_TOKEN_KEY, useValue: 'refreshToken' },
  ```
  This indirection means the actual localStorage key names live in one place (`app.config.ts`) instead of being hardcoded string literals scattered through services. `AUTH_API_URL` itself is injected but doesn't appear to be consumed by anything read in this audit (`AuthService` reads `environment.authApiUrl` directly instead — see below), so it may be vestigial.
- **`service/token-storage.service.ts` — `TokenStorageService`**: injects `WA_WINDOW` (from `@ng-web-apis/common`) and the two token-key tokens. `saveAccessToken`/`saveRefreshToken` no-op if the value is unchanged, else remove-then-set the key (avoids duplicate `storage` events). `getAccessToken`/`getRefreshToken` read directly. `clear()` removes both.
- **`service/contextUser-storage.service.ts` — `ContextUserStorageService`**: identical shape, for the logged-in user's id and role code.
- **`service/jwt.service.ts` — `JwtService`**: wraps `@auth0/angular-jwt`'s `JwtHelperService`. `decodeToken<T>`, `isTokenExpired`, `getUnexpiredDecoded<T>` (returns `null` if empty/expired). **Not invoked anywhere in login, the interceptors, or the guards read for this doc** — it's a ready-made utility that the current flow doesn't call; token expiry is not actually checked client-side today.
- **`service/role.consts.ts`**: `class role { static readonly admin = '_ADMIN_'; static readonly publicUser = '_PUBLIC_USER_' }` — the only two role codes actually checked in guard logic. This is a separate, much smaller concept than the `roles`/`permissions`/`rolepermissions` CRUD libs (§3), which model an arbitrary admin-configurable RBAC table but aren't wired into `AuthService.isAdmin()` — that check is a flat string comparison against this const, not a lookup into the permissions system.
- **`service/auth.service.ts` — `AuthService`** (`providedIn: 'root'`): the session gate.
  - `isLoggedIn()`: if `authState$` (a `BehaviorSubject<boolean|null>`, starts `null`) already has a boolean, returns it via `of(...)` (no network call). Otherwise `GET {environment.authApiUrl}/me` with `withCredentials: true`; success → `true` and caches it; error → caches `false`, swallowed via `catchError`.
  - `isAdmin()`: same caching pattern via `adminState$`, but instead of a network call it reads `ContextUserStorageService.getContextUserRole()` and compares to `role.admin`.
  - `logout()`: `POST {authApiUrl}/logout` with credentials, then sets `authState$` false and navigates to `authRoutes.login` (note: navigates with the whole `Route` object, not `.path` — relies on Angular Router accepting a route object/array loosely; other call sites use `.path` explicitly, see below).
  - `clearAuthState()`, `setAuthenticated()` (also resets an internal `redirecting` flag).
  - `handleUnauthorized()` / `handleForbidden()`: both guarded by a `redirecting` boolean so a burst of parallel 401s/403s only triggers one navigation. `handleUnauthorized` → `authState$.next(false)` + navigate to `authRoutes.login.path`. `handleForbidden` → `adminState$.next(false)` + navigate to `publicRoutes.user_profile.path`. These are called from the interceptor, not from guards.
- **Interceptors** (`libs/auth/interceptors/`):
  - `auth.interceptor.ts` — `AuthInterceptorFn` (the one actually registered, in `app.config.ts:60`): clones every request with `withCredentials: true`; on error, if status is 401 or 403 **and** the URL doesn't contain `/login`, `/logout`, or `/me`, calls `auth.handleUnauthorized()` / `auth.handleForbidden()` respectively; always rethrows.
  - `auth-header.interceptor.ts` — `AuthHeaderInterceptorFn`: reads the access token from `TokenStorageService` and *would* set an `Authorization: Bearer <token>` header, but that `setHeaders` block is commented out (`request.clone({ withCredentials: true })` is all that survives), and **this interceptor is not passed to `withInterceptors([...])` in `app.config.ts`** — only `AuthInterceptorFn` is. So today, `TokenStorageService`'s saved access/refresh tokens are written but never read back into a request. If you want real bearer-token auth in a new project, finish this interceptor and register it; if you want cookie-session auth (what's actually live here), you can drop `TokenStorageService`/`AuthHeaderInterceptorFn` entirely.
- **Guards** (`libs/guards/`):
  - `auth/auth.guard.ts` — `authGuard: CanActivateFn`: `auth.isLoggedIn()` → `true` or `router.createUrlTree(['/login'])` (hardcoded literal path, not `authRoutes.login.path`); same fallback on error.
  - `admin/admin.guard.ts` — `adminGuard: CanActivateFn`: checks `auth.adminState$.value` synchronously first; otherwise `auth.isAdmin()`. Non-admin → redirect to `publicRoutes.user_profile.path` (and caches `false`). On a caught error with `status === 403` → same redirect + cache `false`; any other error → redirect to `authRoutes.login.path`. Uses the typed route constants, unlike `authGuard`.

## 3. Login & Signup (`libs/auth/login`, `libs/auth/signup`)

Each feature is `model.ts` (request/response interfaces) + `*-form.service.ts` (a `NonNullableFormBuilder`-based reactive form, `@Injectable()` — no `providedIn: 'root'`, so it must be listed in a component's `providers:` array, which both `page-login` and `page-signup` do) + `*-api.service.ts` (`providedIn: 'root'`, real `HttpClient` calls). **No barrel**: neither `libs/auth/login/` nor `libs/auth/signup/` has its own `index.ts` — their pieces are consumed by full path, or re-exported piecemeal from `libs/auth/index.ts` (which exports the login/signup model + form-service but, per §2, not `AuthService`/`role.consts`/the API services). Don't assume every feature folder is barreled — check for an `index.ts` before importing through one.

- **`login.model.ts`**: `LoginRequest { email, password }`; `LoginResponse { token, refreshToken?, user?: {id, roleCode} }`.
- **`login-form.service.ts`**: fields `email` (required + email-pattern regex), `password` (required), `rememberMe` (boolean, unused downstream in the files read). A commented-out `phone` field suggests phone-login was considered and dropped for login (unlike signup, which does support phone).
- **`login-api.service.ts` — `LoginApiService.login(payload)`**: `POST {environment.apiUrl}/user/signin` with `withCredentials: true`. `handleLoginResponse` tolerates **two response shapes** — a raw string (treated as just the access token, comment: `// tmp`) or a structured object — and saves whichever fields are present via `TokenStorageService`/`ContextUserStorageService`, then calls `authService.setAuthenticated()`. Redirect logic: if a `ReturnUrl` query param exists and starts with `/`, does a **full page navigation** (`window.location.href = baseUrl + returnUrl`, stripping a trailing `/api` off `apiUrl` first) — this is for a cross-app/legacy redirect target outside the Angular router; otherwise `router.navigate([dashboardRoutes.user])`. On any HTTP error, calls `authService.logout()` (which itself fires a `/logout` request) before rethrowing — meaning a failed login attempt still triggers a logout POST.
- **`signup.model.ts`**: `SignUpRequest { fullName, phone: string|null, email: string|null, password }`; `SignUpResponse { id }`.
- **`signup-form.service.ts` — `SignUpFormService`**: single `identifier` field validated by an inline email-or-BD-phone regex validator (`emailOrPhoneValidator`), separate (non-required) `email`/`phone` fields that the identifier gets split into at the *component* level (see `page-signup.component.ts:48-55`, `isEmail`/`normalizePhone` helpers), `password`/`confirmPassword` with a shared `passwordMatchValidator` (from `libs/common-service/lib/password-match.validator.ts`) as a group-level validator. Also injects `FormValidationErrorsService` for `getErrorMsg(name)` — a helper `LoginFormService` does not have, so error-message rendering is inconsistent between the two forms.
- **`signup-api.service.ts` — `SignupApiService.signup(payload)`**: `POST {apiUrl}/user/signup`. `handleSignUpResponse` is an empty stub (`// handle response here`) — the API service itself does nothing on success; the actual "what happens after signup" logic (clearing/starting the OTP flow, navigating) lives in the **component**, not the service (see §5). `handleSignUpError` special-cases HTTP 409 into a friendlier `"Account already exists"` message, otherwise rethrows the original error.

## 4. OTP module (`libs/otp`) — shared verification primitive

This is the one piece explicitly designed for reuse across two different flows (signup email/phone verification, and forgot-password identity verification), via an `OtpType` enum rather than two separate implementations.

- **`otpType.enum.ts`**: `enum OtpType { Verification = 1, PasswordReset = 2 }`.
- **`otp-api.service.ts` — `OtpApiService`**: `sendOtp(emailOrPhone, otpType)` → `POST {env.apiUrl}/req-otp-verify` with `{destination, OtpType}`; `verifyOtp(destination, otpCode, otpType)` → `POST {env.apiUrl}/verify-account-otp` with `{destination, otpCode, otpType}`. Injects the app's `EnvironmentConfig` via `ENVIRONMENT` token from `libs/core`, rather than importing `environment` directly (the only auth-adjacent service that does DI-based environment injection instead of a static import — worth standardizing on one approach).
- **`otp-state.service.ts` — `OtpStateService extends SimpleStore<OtpState>`** (`providedIn: 'root'`): state shape includes `identifier`, `method: 'email'|'phone'` (auto-derived from whether the identifier contains `@`, in `setIdentifier`), `otpToken`, `otpType`, `loading/error/errorMessage`, `verificationStatus: 'idle'|'sent'|'verified'|'failed'|'expired'`, `otpCode`, `expiresAt` (epoch ms), `timeRemaining` (seconds). Owns a **2-minute countdown timer** (`OTP_DURATION = 2*60*1000`) via `setInterval`, started on successful `sendOtp()` and stopped on verify/expire/reset. `verifyOtp()` short-circuits to an error if `timeRemaining <= 0` before even calling the API. `resendOtp()` = `clearOtpState()` + `sendOtp()`. This is the single source of truth consumed by three different pages (`page-verified`, `page-verifiedotp`, `page-signup`) — none of them keep their own OTP timer/status state.
- **`otp-form.service.ts` — `OtpFormService`**: builds an `identifierForm` and an `otpForm` with validators, plus `setValidationMethod('email'|'phone')` to swap which sub-field is required. **Not actually injected by any of the OTP pages read** (`page-verified.component.ts` and `page-verifiedotp.component.ts` build their own `FormGroup`/`FormControl` inline instead) — treat this as available-but-currently-unused, not as evidence of the "real" pattern.
- **`otp.model.ts`**: `SendOtpRequest/Response`, `VerifyOtpRequest/Response`, plus generic `Otp`/`OtpDto` shapes that don't exactly match what `OtpApiService` actually sends/receives (e.g. it sends `{destination, OtpType}` to `/req-otp-verify`, not the `SendOtpRequest{input, OtpType}` shape aimed at a `/otp-request`-style endpoint) — the models look like an earlier draft that the api service moved past; don't assume the model file is authoritative over the api service's actual request bodies.
- **No barrel**: `libs/otp/` has no `index.ts` at all — every consumer (`page-signup`, `page-verified`, `page-verifiedotp`) imports each file by its full path.

## 5. Forgot-password module (`libs/forgot-password`)

- **`forgot-password.model.ts`**: `ForgotPasswordRequestDto { email, newPassword }`, `ForgotPasswordResponse { success, message }`, `ForgotPassword extends ForgotPasswordResponse { email }`.
- **`forgot-password-api.service.ts` — `ForgotPasswordApiService`**: has **three** methods — `sendOtp(email)` → `POST {apiUrl}/otp-request`, `verifyOtp(email, otpToken)` → `POST {apiUrl}/otp-verify`, and `resetPassword(request)` → `POST {apiUrl}/users/forgot-password-reset`. **Only `resetPassword` is actually called** by the page flow read in this audit (`page-reset.component.ts:124`); `sendOtp`/`verifyOtp` here hit different endpoints (`/otp-request`, `/otp-verify`) than the ones the OTP module actually uses (`/req-otp-verify`, `/verify-account-otp`) and appear to be an earlier, now-bypassed implementation of the same concept OTP module now owns. Treat these two methods as dead/duplicated — don't wire a new project's forgot-password screen to them.
- **`forgot-password-state.service.ts` — `ForgotPasswordStateService extends SimpleStore<ForgotPasswordState>`** (`providedIn: 'root'`): state = `email, loading, error, errorMessage, success, successMessage, otpVerified, resetCompleted`. `setEmail`, `sendOtp()`/`verifyOtp()` (call the API methods above — again, not actually invoked by the live page flow, see previous point), `markOtpAsVerified()` (called by `page-reset` after it independently confirms `OtpStateService`'s status is `'verified'` — i.e. verification truth lives in `OtpStateService`, and this flag is just a local mirror set by the component, not derived from a real second check), `resetPassword(newPassword, confirmPassword)` (validates non-empty + match + `otpVerified` client-side before calling the real API), plus a full set of getters (`isLoading`, `hasError`, `getErrorMessage`, etc.) and `clearState()`.
- **`index.ts`**: unlike login/signup/otp, this module *does* have a barrel — and it's a clean, literal instance of the four-stage chain: `export * from './forgot-password.model'` → `export * from './forgot-password-api.service'` → `export * from './forgot-password-state.service'`, in that exact order (interface → api-service → state-service → re-exported via index). This is the clearest example in the repo of the "interface → service → state → index" convention; the RBAC CRUD libs in §6 follow the same barrel idea but with an extra mock `*-data.service.ts` stage inserted between api and state.

## 6. RBAC entity CRUD libs (`libs/{role,permissions,rolepermissions,token,mfalogs,mfsettings,emailverifications}`)

These model admin-configurable data (as opposed to the two hardcoded role strings in `role.consts.ts`) and follow a different, four-file convention. Using `emailverifications` as the fully-representative example (confirmed structurally consistent with `mfalogs`/`mfsettings`):

- **`*.model.ts`**: plain interface, e.g. `EmailVerification { id: bigint, user_id: bigint, token: string, expires_at: string, verified_at?: string }`. `role.model.ts` uses a DTO/entity split (`RoleDto` without `id`, `Role extends RoleDto` with `id`); `rolepermission.model.ts` is just the join shape `{ role_id, permission_id }`; `token.model.ts` similarly splits `TokenDto`/`Token`.
- **`*-api.service.ts`**: real `HttpClient` CRUD (`getAll/getById/create/update/delete`, plus an entity-specific action like `verifyToken` or `toggleEnabled`) — **but the base URL is a hardcoded placeholder**, e.g. `emailVerification-api.service.ts:10` → `'https://api.example.com/email-verifications'`, `mfalog-api.service.ts:10` → `'https://api.example.com/mfa-logs'`, `mfasetting-api.service.ts:10` → `'https://api.example.com/mfa-settings'`. None of these read `environment.apiUrl`.
- **`*-data.service.ts`**: an in-memory mock — a literal seed array plus `getAll/create/update/delete` methods with the *same signatures* as the api-service, returning `of(...)`. This is what's actually exercised today.
- **`*-state.service.ts`**: a bare `BehaviorSubject<T[]>` (not `SimpleStore` — a plain `Injectable` class holds `verificationsSubject` directly) that calls into the **data service**, not the api service — `loadVerifications()` subscribes to `dataService.getAll()`. **This means the admin CRUD screens for these entities are wired to mock, in-memory data, not the real backend, until someone swaps the state service's dependency from `*-data.service` to `*-api.service`.**
- **`index.ts`**: barrel export.

This is a materially different pattern from the OTP/forgot-password state services (§4–5), which are real `SimpleStore` subclasses hitting live endpoints. Don't confuse the two: "does this feature have a `-data.service.ts`" is the tell for "this is currently mock-backed admin CRUD," not "this is the standard pattern for all state services."

## 7. Routing (`app/pages/auth/auth.route.ts`, `app/app.routes.ts`)

- **`auth.route.ts`**: exports a typed `authRoutes: AuthRoutes` object (`AuthRoutes` = a type with named keys — `default, login, todo, profile, reset, signup, verified, verifiedotp` — each mapped to `Route`). Every entry uses `loadComponent: () => import(...).then(m => m.XComponent)` and `resolve: { layout: setLayout(PageLayout.Public) }` (from `libs/common-components`) — a route-resolver-driven way of tagging which chrome/layout a page should render with, rather than nesting layouts via component composition. `default` redirects to `'admin/user'` (note: this looks stale/inconsistent with the rest of the auth routes, which are all public-layout pages — worth double-checking against the actual dashboard route prefix in a new project rather than copying verbatim).
- **`app.routes.ts`**: defines `groupedRoutes: AppRouteGroups = [authRoutes, dashboardRoutes, addressRoutes, publicRoutes, notFoundRoutes]` (each itself a typed named-Route object, same shape as `authRoutes`), then a loop that:
  1. Flattens every group's `Object.values(...)` into one `Route[]`.
  2. Programmatically appends `authGuard` to every route in `dashboardRoutes`, `addressRoutes`, `publicRoutes` (not `authRoutes` or `notFoundRoutes`).
  3. Additionally appends `adminGuard` to every route in `dashboardRoutes`, `addressRoutes` (not `publicRoutes`).
  
  So: auth pages are open to everyone (as they must be), "public" authenticated pages (e.g. user profile — confusingly named `publicRoutes` but guarded by `authGuard`) require login but not admin, and dashboard/address pages require both login and admin. This guard-composition-by-route-group-identity pattern (comparing `routeGroup === dashboardRoutes` by reference) is the key convention to replicate — it keeps guard wiring in one place instead of repeating `canActivate: [...]` on every route literal.

## 8. Root wiring (`app/app.config.ts`)

Relevant providers (full file is short, see the file directly for the rest): the five auth injection tokens with their concrete values (§2), `provideHttpClient(withXsrfConfiguration({}), withJsonpSupport(), withInterceptors([AuthInterceptorFn]), withInterceptorsFromDi())` — confirms only `AuthInterceptorFn` is active, `provideRouter(appRoutes, ...)`, `provideZonelessChangeDetection()`, `provideStore()` (`@ngrx/store`, registered but not obviously consumed by the auth module itself — it uses the RxJS `SimpleStore` family instead).

## Flow sequences (component → service → endpoint)

**Login** — `page-login.component.ts` (`LoginFormService.form`) → `onSubmit()` → `LoginApiService.login(formData)` → `POST {apiUrl}/user/signin` (`withCredentials`) → on success, tokens/context-user saved (§3), `authService.setAuthenticated()`, then either `window.location.href` to a `ReturnUrl` or `router.navigate([dashboardRoutes.user])`; on error, a PrimeNG toast and `authService.logout()` fires.

**Signup → email/OTP verification** — `page-signup.component.ts` (`SignUpFormService.form`, `identifier` split into `email`/`phone`) → `SignupApiService.signup(payload)` → `POST {apiUrl}/user/signup` → on success: `otpState.clearOtpState(); otpState.setIdentifier(identifier); otpState.setOtpType(OtpType.Verification); otpState.sendOtp()` → `POST /req-otp-verify` → navigate `/verifiedotp` → `page-verifiedotp.component.ts` collects a 4-digit code into `otpControl`, guards against `otpStateService.isOtpValid()` (timer not expired) before calling `otpStateService.verifyOtp()` → `POST /verify-account-otp` → on `verificationStatus === 'verified'` and `otpType === Verification`, navigate `/login`.

**Forgot password** — `page-verified.component.ts` (despite the name, this is the *request* step: user enters email/phone) → `otpStateService.setOtpType(OtpType.PasswordReset); setIdentifier(identifier); sendOtp()` → navigate `/verifiedotp` → same OTP verify step as above, but on success with `otpType === PasswordReset`, navigate `/reset` → `page-reset.component.ts` on init reads `otpStateService.getState()`, **requires `verificationStatus === 'verified'`** or bounces back to `/verified`, copies the identifier into `forgotPasswordStateService.setEmail(email)` and calls `markOtpAsVerified()` (a local mirror flag, see §5) → user submits new password → `forgotPasswordStateService.resetPassword(pw, confirmPw)` → `POST {apiUrl}/users/forgot-password-reset` → on success, clears both `otpStateService` and `forgotPasswordStateService`, navigates to `/login`.

## Replicate-in-a-new-project checklist

1. **Store kit** — copy `libs/store/lib/*` verbatim (deps: `rxjs`, `radash`, `qs`, `destr`). No auth coupling.
2. **Auth core** — copy `libs/auth/injector`, `service/token-storage.service.ts`, `service/contextUser-storage.service.ts`, `service/auth.service.ts`, `service/role.consts.ts` (deps: `@ng-web-apis/common`). Decide up front whether you want `JwtService`/bearer tokens (finish `AuthHeaderInterceptorFn` and register it) or cookie-session only (delete both and skip `@auth0/angular-jwt`) — don't carry over the half-wired state.
3. **Guards + interceptor** — copy `libs/guards/auth`, `libs/guards/admin`, `libs/auth/interceptors/auth.interceptor.ts`; register the interceptor in your `app.config.ts`'s `provideHttpClient(withInterceptors([...]))`; provide the five injection tokens with real values there too.
4. **Login/Signup** — build `model.ts`/`*-form.service.ts`/`*-api.service.ts` per §3 against your real `/user/signin` and `/user/signup`-equivalent endpoints.
5. **OTP module** — copy `libs/otp` once; parametrize by an `OtpType`-style enum from day one so you don't end up with a second bespoke OTP implementation (the mistake already present in this repo's `forgot-password-api.service.ts`, §5).
6. **Forgot-password** — build only the parts OTP can't cover (email capture + the actual `resetPassword` call); explicitly reuse `OtpStateService` for the verification step instead of writing parallel `sendOtp`/`verifyOtp` methods.
7. **Routing** — define one typed named-`Route` object per section (`auth.route.ts` style); in your root routes file, flatten multiple such groups and attach guards by comparing group identity (§7), rather than repeating `canActivate` per route.
8. **Admin CRUD entities** (if/when needed) — use the model/api/data/state four-file split from §6, but point `*-api.service.ts` at real endpoints immediately and either skip the mock `*-data.service.ts` entirely or clearly gate it behind a dev/demo flag — and wire `*-state.service.ts` to the **api** service, not the data service, once a real backend exists.
